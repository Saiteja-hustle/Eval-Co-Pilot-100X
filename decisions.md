## AI decided — Stage 3
- `schema.sql`: three tables exactly as the task listed (which matches PRD section 10 plus a `created_at` on `questions` and `answers` that the PRD's own table didn't name but the task asked for explicitly). Every table has a nullable `user_id uuid` column, no default, no foreign key to `auth.users` yet — Stage 6 (login/RLS) is what fills it in and turns RLS on. `id` columns use `uuid primary key default gen_random_uuid()`, which needs the `pgcrypto` extension; the schema turns that extension on with `create extension if not exists pgcrypto` since Supabase doesn't always have it on by default. `answers.run_id` and `answers.question_id` are foreign keys to `runs(id)` / `questions(id)`, per the PRD's "Answer points to Run, Answer points to Question" arrow. No RLS statement anywhere in the file, per the task's explicit "do NOT turn on RLS yet".
- `requirements.txt`: added `supabase` (the Python client) and `python-dotenv` (loads `.env` locally). Nothing else changed.
- `main.py` calls `load_dotenv()` once at import time, then reads `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` from `os.environ`. If both are set, it builds one `supabase` client at startup and reuses it for every request; if either is missing (e.g. a fresh clone with no `.env` yet), `supabase` stays `None` instead of crashing the whole app on import — only the routes that actually need the database fail, and only when called.
- `POST /api/runs` is new: takes `app_address`, `question_field`, `answer_field`, `global_wrong_text`, inserts exactly one row into `runs`, and returns that row's generated `id`. It does not touch `questions` or `answers` — those are per-question, not per-run.
- `POST /api/run-question` got one new **optional** field, `run_id` (defaults to `None`/absent, so every existing caller that doesn't send it behaves byte-for-byte as before). `check_one(...)` still runs first and its Pass/Fail result is computed and ready to return no matter what happens next. Only if `run_id` is present does the route also try to save: one `questions` row (`question_text`, `good_answer_includes` — a fresh row per answer, not deduplicated, since the PRD's 3-table model doesn't ask for question reuse across runs) and then one `answers` row linking that question and that run to the Pass/Fail outcome. That whole save is wrapped in one `try/except Exception`, so a Supabase outage, a bad `run_id`, missing credentials, or any other DB error can never turn a working check into a 500 — the same `result` dict goes out either way, with `result["saved"]` set to `True` on success or `False` on any failure (including when `supabase` is `None`). This directly implements the task's "A database error must never stop the check" rule.
- `GET /api/runs/{run_id}` fetches the one `runs` row (`.single()`, since `run_id` is a primary key and there's exactly one or none) plus every `answers` row whose `run_id` matches, and returns both under `{"run": ..., "answers": ...}`. This is intentionally the simplest shape that answers PRD test query 1 ("every answer in one run with pass_fail and fail_reason") — no join, no extra fields, nothing the task didn't ask for.
- `index.html`: the only JavaScript change is inside the existing `runBtn` click handler, right before the per-question loop starts. It now does one `POST /api/runs` call with the four setup fields already read off the page, and keeps the returned `id` in a new `runId` variable (`null` if the call fails or Supabase isn't configured, exactly like the existing network-error handling pattern already in this file). That `run_id` is then added as one new key in the JSON body already being sent to `/api/run-question` on every loop iteration. No other markup, styling, id, class, event listener, or visible text in the page was touched — this is the "smallest change needed" the task asked for.
- Did not add a `user_id` anywhere in the request bodies or the Python code (frontend or backend) — the task says `user_id` is nullable "for now" and nothing in Stage 3 asks for a value to be supplied yet. The column exists in the schema so Stage 6 doesn't need a migration, but it's left `NULL` on every insert until login exists.
- Verified locally (no real Supabase project connected in this sandbox): `GET /api/hello` → 200 unchanged; `GET /` → 200 unchanged; `POST /api/run-question` with no `run_id` → identical response shape to before (no `saved` key); same call with a `run_id` but no Supabase credentials configured → still returns the correct Pass/Fail result, plus `"saved": false`, with no crash and no 500. ## AI decided — Stage 5
- Scope: `main.py` and `index.html` only. `checks.py`/`check_one` untouched (confirmed byte-for-byte identical to the Stage 3 version). `schema.sql` and the three tables untouched — no new table or column; rerun/compare uses only `questions.id`/`question_text`/`good_answer_includes` and `answers.run_id`/`question_id`/`pass_fail`/`fail_reason`/`app_answer`, all of which already existed.
- `POST /api/run-question` gained one more optional field, `question_id` (defaults to `None`, so a caller that never sends it — including every existing caller — behaves exactly as before, down to the response shape not gaining a `question_id` key). When `question_id` is sent and `run_id` is also sent, the route skips the `questions` insert and instead does an unconditional `update` on that question row's `question_text`/`good_answer_includes`, then inserts the new `answers` row pointing at that same `question_id` and the new `run_id`. The update is unconditional (not "select first, compare, update only if different") — the end state is identical either way (the row ends up holding the current text), and skipping the extra read-before-write keeps it to one round trip instead of two. On success the response gains `"question_id"` (the reused or newly-created id) in addition to the existing `"saved"` key; on any DB exception it's still `"saved": false` with the Pass/Fail result returned untouched, exactly as Stage 3 already did.
- `GET /api/compare?run_a=&run_b=` is new, read-only, and stores nothing. It loads `answers` for both runs, matches rows purely by `question_id` (never by question text, since text can change between runs), and classifies each question present in both runs as `Fixed` (Run A Fail -> Run B Pass), `Broke` (Run A Pass -> Run B Fail), or `Same` (anything else, including Fail->Fail with a different reason). A question answered in only one run is `"Only in Run 1"` / `"Only in Run 2"`. When both runs answered the same `question_id` more than once (shouldn't normally happen, but isn't prevented either), the row is matched by last-inserted order (`.order("created_at")`, last one wins when building the per-question-id dict) rather than crashing on a duplicate.
- Unknown/missing run ids: a missing `run_a`/`run_b` query param is FastAPI's own 422 (a clear error, no server code needed); a run id that doesn't exist in `runs` is checked explicitly and returns a 404 with the bad id named; any Supabase connection failure during the lookup returns a 502 instead of an unhandled 500. `supabase is None` (no credentials configured) returns a 503. None of these can crash the process.
- The summary block returns `passed`/`total` per run plus the `Fixed`/`Broke`/`Same` counts; nothing from it is written back to the database — it's computed fresh on every call, per the task's "nothing about Fixed/Broke/Same is stored" rule.
- `index.html`: kept every existing id, class, field name, label, button, table header, and message text byte-for-byte — verified by diffing the file: nothing before the `runBtn`/`statusMsg` block changed except two added CSS rules (`.fixed`/`.broke`/`.same`/`.only` pills, reusing the same color variables as `.pass`/`.fail`, and a hidden-by-default `#rerunBtn`). Everything else is additive: a new `#rerunBtn` button, a new `#compareCard` section (summary line + a 4-column table: Question / Run 1 / Run 2 / Fixed-Broke-Same), and new JS.
- Page memory: each row's reused `question_id` is stored as `row.dataset.questionId` the moment `/api/run-question` returns one — this survives add/delete of other rows for free since it lives on the row's own DOM node, no separate array to keep in sync. `lastRunId` and `baseRunId` are the two run ids kept in page memory ("run_id... in page memory" from the task) — `lastRunId` is always the most recently completed run; `baseRunId` is set to `lastRunId` the moment "Edit questions and run again" is clicked, and is what gets compared against the next run once it finishes (then cleared back to `null`).
- "Makes the question boxes editable again" was read as: after any run finishes, the question/includes text inputs are disabled (locked) so the report you're looking at clearly reflects what was actually run, and only "Edit questions and run again" re-enables them. Add-question/delete-row buttons are never locked — adding a fresh row (with no `question_id`) and deleting a row are always available, matching "questions added during a rerun have no question_id: send them without one."
- Comparison runs are always between *consecutive* runs — the run active right before "Edit questions and run again" was clicked, and the run that finishes next — not always against the very first run ever made. This reads more naturally for a page that supports Run 2, Run 3, Run 4...: each rerun shows "what changed since last time," not a fixed baseline. If Tj wants it pinned to the literal first run instead, that's a one-line change (store the very first `runId` once and never overwrite it).
- The compare table's Run 1 / Run 2 cells show the Pass/Fail pill (same `.pass`/`.fail` classes already used in the existing report table) and, only for a Fail, the fail reason as a small muted line underneath — matching "show Pass or Fail, and the fail reason under Fail."
- The existing report table (`#reportCard`) is untouched in behavior: it always shows the run that just finished, same as before Stage 5. The new compare table is a separate card below it, shown only once a second (or later) run completes with a `baseRunId` to compare against.
- Did not add any confirmation dialog or "are you sure" before unlocking fields for a rerun, since nothing is deleted or lost by re-running — Run 2 only ever adds rows, per the existing "Run 2 adds rows and never overwrites Run 1" decision.
- Verified locally (see note under "Stage 5 — how it was tested" below): `GET /api/hello` and `GET /` unchanged; `POST /api/run-question` with no `question_id` is byte-identical to the old response shape; sending a `question_id` reuses the row instead of inserting a new one and updates its text in place; `GET /api/compare` correctly classifies Fixed/Broke/Same/Only-in-Run-1/Only-in-Run-2 and returns a 404 (not a crash) for an unknown run id; the full page flow (run, lock, click Edit, edit a question's includes text, add a new question, run again, see the compare table with colored Fixed/Broke/Same pills) was driven end-to-end in a real headless browser.

## Known limits
- Reruns are only possible while the page is open — `question_id` lives only in that page's DOM (`row.dataset.questionId`); closing or reloading the page loses the link back to earlier questions, and the next run starts everything as brand-new questions.
- Fixed or Broke can flip for reasons that have nothing to do with a real fix or a real regression: Pratik's app words its answers differently on every call (see the Stage 1 "3 m2" note above), so the same question can Pass on one call and Fail on the next purely from wording, independent of any edit Tj made.
- Run 1 is judged by the old "includes" text. When Run 2 edits a question's "good answer includes" box, that edit updates the question row going forward, but Run 1's saved Pass/Fail was already computed (and stored) against the old text at the time Run 1 ran — editing afterward never recomputes or changes Run 1's stored result.
